Plant rental — current backend flow

This page describes what the existing API actually does today, so product and mobile can align without assuming a different state machine. Base path: /api/v1 (see Swagger at /v1/api if enabled).

Intentional scope: this doc matches implemented behaviour (Prisma OrderStatus, workflowMeta JSON, mock payments). It is not a full “ideal” spec: some product docs use labels like APPROVED or EXPIRED that are not separate enum values in the database.

0. Vendor onboarding & team management (Phase 00)

Profile, service coverage, catalogue packages, and nursery staff (create/update/credentials/status) live primarily under /api/v1/nurseries and /api/v1/vendor/packages. For a single JSON response that lists every route and your completion flags, call: 

GET /api/v1/vendor/onboarding  (Authorization: Bearer, role VENDOR)

That endpoint returns checks, counts, minimum_ready_for_package_sales, recommended_next, and canonical_flow (ordered steps with method/path).

0b. Gardener onboarding — staff vs freelance

Staff: vendors create accounts, set passwords (reset), update profile fields, and deactivate — no self-registration path required for the staff user beyond login. Freelance: the user registers as GARDENER, then POST /api/v1/gardeners/profile with is_freelancer and hourly_rate, plus skills / areas / availability. 

GET /api/v1/gardeners/onboarding

Public JSON catalog: staff_vendor_managed, freelance_self_service, public_discovery, and freelance_maintenance_jobs (REST paths for /api/v1/freelance-jobs).

1. Order status (what the DB uses)

Orders use Prisma OrderStatus, for example:

StatusTypical meaning in this app
PENDINGSubmitted; awaiting vendor action.
CONFIRMEDVendor has approved with plant selections; customer may still need to pay (check paymentStatus).
PROCESSINGVendor sent order to processing (after payment is paid where required).
OUT_FOR_DELIVERYUsed when delivery is in progress (e.g. after customer confirmed a slot in contract flow paths).
DELIVEREDDelivery completed; rental lines can become active.
COMPLETEDOrder/rental lifecycle completed.
SLOT_PROPOSEDVendor ran propose-delivery-slots; workflowMeta.delivery holds proposals + slotExpiresAt.
SLOT_CONFIRMEDCustomer confirmed a slot via customer-delivery-response; may await payment (paymentWindowExpiresAt in meta).
AWAITING_PAYMENTPayment initiate path after slot confirmation (see payments service).
CANCELLEDCancelled (customer/vendor/system depending on path).
EXPIREDUnpaid checkout or stale slot/payment window (internal jobs).
RETURNEDLegacy / return-related terminal state where used.

Product tip: show “Pay now” when paymentStatus === PENDING (or your gateway state), not only from status. After vendor approve, the API may set status to CONFIRMED while payment is still pending.

2. Customer journey (core rental order)

A — BROWSE & CART
  1. Discovery: GET /api/v1/nurseries, GET /api/v1/nurseries/:id, plants listings.
  2. Cart: GET/POST/PUT /api/v1/cart/... (packages may use existing public package APIs unless the app is switched to vendor packages).
  3. Checkout: POST /api/v1/orders/checkout → creates order (typically PENDING).
B — VENDOR APPROVE
  1. Vendor: PUT /api/v1/orders/vendor/orders/:order_id/approve with plant_selections[] (every line must be covered).
  2. Backend sets order to CONFIRMED and stores selections. Customer should be prompted to pay if paymentStatus is not PAID.
  3. Doc vs DB naming: product copy may say APPROVED — it maps to CONFIRMED. Vendor reject uses CANCELLED + cancelled_by vendor user; UI may label REJECTED.
B2 — CUSTOMER CANCEL & RENTAL HUB
  1. Cancel: POST /api/v1/orders/:order_id/cancel — PENDING, CONFIRMED unpaid, or within ORDER_CUSTOMER_CANCEL_WINDOW_HOURS (default 8) from order.created_at while still unpaid and before OUT_FOR_DELIVERY (includes SLOT_PROPOSED inside the window).
  2. Rental list (aggregated): GET /api/v1/orders/customer/active-rentals returns ongoing, overdue, pickup_pending (doc “PICKUP_PENDING”: line RETURNED, order not COMPLETED), pending_vendor_extensions, plus items[] with customer_rental_bucket, penalty, flags, ui_hints.
  3. Extension vendor gate (optional): set RENTAL_EXTENSION_VENDOR_APPROVAL=true — then vendor POST .../rental-extensions/:extension_id/approve|reject before customer pays.
C — PAYMENT
  1. POST /api/v1/payments/initiate (mock gateway).
  2. POST /api/v1/payments/verify with gateway fields — on success, payment is captured and order payment moves toward paid; optional Idempotency-Key header replays the same result for the same body.
D — VENDOR PROCESS & DELIVERY
  1. Slot-before-payment variant: vendor may propose while order is still CONFIRMED unpaid — POST /api/v1/orders/vendor/orders/:order_id/propose-delivery-slots (mirror: POST /api/v1/orders/:order_id/propose-delivery-slots).
  2. Paid fulfilment path (typical): after PAID, vendor POST /api/v1/orders/vendor/orders/:order_id/process → PROCESSING.
  3. Create / merge slots in workflowMeta: propose body fields and JSON shapes — §1b and Swagger examples on each route.
  4. Customer reply: POST /api/v1/orders/:order_id/customer-delivery-response (CONFIRM / reschedule / gardener preference).
  5. Optional maintenance + hints: POST /api/v1/orders/vendor/orders/:order_id/assign-gardener — merges workflowMeta.assignGardener when delivery_slots supplied.
  6. Complete delivery: POST /api/v1/orders/vendor/orders/:order_id/complete-delivery → DELIVERED; optional body → workflowMeta.deliveryCompletion.

Docs vs one UI action: the product may show “schedule delivery” as one screen, but the backend may require more than one call (e.g. propose slots, assign gardener). See §1b for the contract.

E — RETURN (contract-style)
  1. Vendor: POST .../vendor/orders/:order_id/initiate-return (pickup slots in body → workflowMeta).
  2. Customer: POST /api/v1/orders/:order_id/customer-return-response.
  3. Vendor: POST .../complete-return with per-line condition / restock flags.
  4. Customer cancel (pre-delivery / window): POST /api/v1/orders/:order_id/cancel — see §B2.
F — OVERDUE & PENALTY
  1. Daily cron (rental_penalty_sweep, 01:00 server time): sets rental lines to OVERDUE when rent_end_date < today; upserts OrderPenalty (days × daily rate × PENALTY_DAILY_MULTIPLIER, default 1).
  2. GET /api/v1/orders/:order_id/penalty — live accrual for customer.
  3. POST /api/v1/payments/initiate with payment_for: "PENALTY", reference_id = order UUID.
  4. POST /api/v1/payments/verify — marks penalty PAID, restores OVERDUE lines to ACTIVE, notifies customer + vendor.
  5. POST /api/v1/orders/:order_id/finalize-penalty — vendor/collection metadata (optional).

Manual ops: POST /api/v1/internal/jobs/orders/penalty-sweep (admin). Env: PENALTY_CRON_ENABLED, PENALTY_DAILY_MULTIPLIER.

G — RENTAL EXTENSION (single policy)
  1. Canonical: POST /api/v1/orders/:order_id/items/:item_id/extend-rental — body new_end_date or additional_weeks. All rules enforced by RentalExtensionPolicyService (order DELIVERED/COMPLETED, rental ACTIVE/EXTENDED/OVERDUE, 7-day window unless already overdue, plant availability).
  2. Creates RentalExtension, pending Payment with metadata.rental_extension_id, reschedules MaintenanceTask visits, notifies customer/vendor/gardener.
  3. Pay: payment_for: "RENTAL_EXTENSION", reference_id = extension UUID.
  4. Legacy (delegates to same policy): POST /api/v1/rentals/:id/extend — prefer orders route for new apps.

Do not implement a second extension API in mobile — both paths call the same module.

H — ORDER COMPLAINTS (Foodpanda-style)
  1. Customer: POST /api/v1/orders/:order_id/complaints — subject, description, optional attachments[].
  2. Backend sends IN_APP notifications to vendor (nursery owner) and all admins.
  3. Vendor inbox: GET /api/v1/orders/vendor/complaints.
  4. Admin dashboard (ready to wire): GET /api/v1/admin/order-complaints.
  5. Customer history: GET /api/v1/orders/my-complaints.

Admin team: you can implement the dashboard list against GET /api/v1/admin/order-complaints now — notifications already fire on create.

Vendor rental lifecycle (dashboard buckets)

GET /api/v1/vendor/rentals?bucket=ONGOING|DUE_TODAY|OVERDUE|COMPLETED&page=&limit=

Canonical board for nursery rental line items. Response includes counts (ongoing, due_today, overdue, completed) for badges plus one bucket’s items[] (OrderItem rows + plant + customer + delivery address). Days use the server local midnight; default bucket=ONGOING. Legacy flat list: GET /api/v1/orders/vendor/rentals/active (status=DUE_TODAY|OVERDUE or all in-flight).

4. What this HTML deliberately does not promise

  • Exact expiry timings for slots, payment windows, and unpaid orders: OrderStatus includes EXPIRED where implemented — confirm TTL env vars and cron / internal jobs in your deployment.
  • Full slot state machine (HELD, RELEASED, etc.) in SQL — many flows use workflowMeta JSON instead.
  • POST /api/v1/cart/packages and package-first checkout: optional; core checkout still supports individual plant lines.
