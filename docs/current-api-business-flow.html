Plant rental — current backend flow

This page describes what the existing API actually does today, so product and mobile can align without assuming a different state machine. Base path: /api/v1 (see Swagger at /v1/api if enabled).

Intentional scope: this doc matches implemented behaviour (Prisma OrderStatus, workflowMeta JSON, mock payments). It is not a full “ideal” spec: some product docs use labels like APPROVED or EXPIRED that are not separate enum values in the database.

1. Order status (what the DB uses)

Orders use Prisma OrderStatus, for example:

StatusTypical meaning in this app
PENDINGSubmitted; awaiting vendor action.
CONFIRMEDVendor has approved with plant selections; customer may still need to pay (check paymentStatus).
PROCESSINGVendor sent order to processing (after payment is paid where required).
OUT_FOR_DELIVERYUsed when delivery is in progress (e.g. after customer confirmed a slot in contract flow paths).
DELIVEREDDelivery completed; rental lines can become active.
COMPLETEDOrder/rental lifecycle completed.
CANCELLEDCancelled (customer/vendor/system depending on path).

Product tip: show “Pay now” when paymentStatus === PENDING (or your gateway state), not only from status. After vendor approve, the API may set status to CONFIRMED while payment is still pending.

2. Customer journey (core rental order)

A — BROWSE & CART
  1. Discovery: GET /api/v1/nurseries, GET /api/v1/nurseries/:id, plants listings.
  2. Cart: GET/POST/PUT /api/v1/cart/... (packages may use existing public package APIs unless the app is switched to vendor packages).
  3. Checkout: POST /api/v1/orders/checkout → creates order (typically PENDING).
B — VENDOR APPROVE
  1. Vendor: PUT /api/v1/orders/vendor/orders/:order_id/approve with plant_selections[] (every line must be covered).
  2. Backend sets order to CONFIRMED and stores selections. Customer should be prompted to pay if paymentStatus is not PAID.
C — PAYMENT
  1. POST /api/v1/payments/initiate (mock gateway).
  2. POST /api/v1/payments/verify with gateway fields — on success, payment is captured and order payment moves toward paid; optional Idempotency-Key header replays the same result for the same body.
D — VENDOR PROCESS & DELIVERY
  1. After payment is PAID (and order CONFIRMED), vendor: POST /api/v1/orders/vendor/orders/:order_id/process → PROCESSING.
  2. Propose delivery slots (contract path): POST .../propose-delivery-slots with delivery_slots[] — stored in order.workflowMeta.
  3. Assign gardener (maintenance schedule + optional slot hints): POST .../assign-gardener (existing). Extra slot arrays can be merged into workflowMeta when sent.
  4. Customer picks a slot (contract path): POST /api/v1/orders/:order_id/customer-delivery-response (action: CONFIRM with selected_slot_id, or request different time).
  5. Complete delivery: POST .../complete-delivery — optional JSON body is merged into workflowMeta.deliveryCompletion; rental lines are activated as implemented in the service.

Docs vs one UI action: the product may show “schedule delivery” as one screen, but the backend may require more than one call (e.g. propose slots, then assign gardener). The client should sequence calls or the backend can be extended later to bundle them.

E — RETURN (contract-style)
  1. Vendor: POST .../vendor/orders/:order_id/initiate-return (pickup slots in body → workflowMeta).
  2. Customer: POST /api/v1/orders/:order_id/customer-return-response.
  3. Vendor: POST .../complete-return with per-line condition / restock flags.
  4. Customer cancel pre-payment: POST /api/v1/orders/:order_id/cancel (allowed only in early states per server rules).
F — PENALTY (simplified API)
  1. GET /api/v1/orders/:order_id/penalty
  2. POST /api/v1/orders/:order_id/finalize-penalty

Accrual rules may be simpler than a full finance spec; treat as integration surface and confirm numbers with backend for production.

3. Parallel flows (separate from nursery rental order state machine)

Vendor packages (own catalogue)

POST/GET/PUT/DELETE  /api/v1/vendor/packages

CRUD for vendor-defined packages. The legacy public /api/v1/packages may still be used by older clients until the app migrates.

Staff gardeners (vendor-created accounts)

POST/GET/PUT  /api/v1/nurseries/my-nursery/gardeners[...]  (create, get, update, status, reset-credentials)

Aligned with “vendor issues credentials” flows; not invite-code onboarding.

Freelance jobs (Basic tier add-on in product copy)

/api/v1/freelance-jobs  (create, my-requests, open, accept, my-jobs, start, complete, review)

Independent of nursery task assignment; uses FreelanceJob records.

Preferences (recommender)

GET/PUT  /api/v1/preferences/recommendation  →  POST /api/v1/ai/recommender/recommend  (optional body overrides)

Internal / admin (ops)

POST /api/v1/internal/jobs/...  (admin) · GET/PUT /api/v1/admin/settings/freelance-match-config · manual-orders

4. What this HTML deliberately does not promise

  • Automatic 6-hour expiry with a dedicated EXPIRED status (unless you add a job + rules — verify with latest orders + cron code).
  • Full slot state machine (HELD, RELEASED, etc.) in SQL — many flows use workflowMeta JSON instead.
  • Identical labels to a marketing PDF: map UI copy to the fields above (status + paymentStatus + workflowMeta).
